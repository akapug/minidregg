# ML-KEM provider review — 2026-10-02

Production now pins aws-lc-rs 1.18.1 with default features disabled and `non-fips` enabled. The previous working RustCrypto ml-kem 0.2.3 adapter remains captured in the isolated differential harness; its wire representation did not change. Existing baseline dependency versions remain pinned. Nine dependency tuples were added; no baseline tuples were removed.

## Executed differential checks

`aws-provider-check.log` records seven passing tests. Thirty-two keys generated by each provider were imported and exercised in both directions with standard ML-KEM-768 public/secret/ciphertext lengths 1184/2400/1088 bytes. For 128 corrupted ciphertexts, both providers produced exactly equal implicit-rejection secrets; incorrect lengths failed. Sixteen keys from each provider were also tested in both complete hybrid wrapping directions (64 envelopes), preserving X25519/HKDF/XChaCha framing and generation binding.

AWS-LC Rust key import is principally a length check. An invalid modulus public key imports but encapsulation fails. A secret key with a corrupt embedded public-key hash imports but decapsulation fails, as does the tested all-zero secret key. Import success must never be presented as full validation. Valid-length corrupted ciphertexts use implicit rejection rather than an externally distinguishable decapsulation error. The encrypted custody journal authenticates stored secret bytes; malformed-key tests do not exhaust every malformed input.

The actual production adapter and retained-state component suite passed eight selected nextest tests (seven substantive plus subprocess helper), including crash lock recovery and contested epoch settlement. Production isolated `cargo check --locked --offline --jobs 2` passed. These are executable component checks, not a protocol security proof or the final source/native journey.

## Maintenance and build cost

[rustpq/pqcrypto](https://github.com/rustpq/pqcrypto) was archived September 16, 2026 and disclaims future security fixes; it was not added. Cached RustCrypto ml-kem 0.2.3 documents that it has not been independently audited. [aws-lc-rs](https://github.com/aws/aws-lc-rs) provides an actively maintained AWS-LC implementation and a usable ML-KEM-768 API without changing retained key formats.

The isolated initial AWS C build used two jobs and took 14.10 seconds; the differential target initially occupied approximately 101 MiB. Adding all complete-envelope dependencies raised that mixed-provider target to about 182 MiB. This is a scratch build measurement, not AWS alone's incremental footprint. A cold production target check took 33.6 seconds. The C/CMake build is a real additional toolchain and maintenance cost.

## Assessment scope

The pinned aws-lc-sys 0.45.0 vendor metadata identifies AWS-LC commit `02561621ffa4cf17c0c4f70bc11a82df36b42ae9`. Its ML-KEM implementation imports mlkem-native with AWS-specific FIPS202 integration. [mlkem-native](https://github.com/pq-code-package/mlkem-native) documents CBMC proofs of C memory/type safety and HOL-Light assembly proofs of functional correctness, memory safety and secret-independent timing under their stated models.

Its [soundness statement](https://github.com/pq-code-package/mlkem-native/blob/main/SOUNDNESS.md) explicitly limits those claims: C functional correctness and constant time are not proved; there is no complete formal ML-KEM specification or automatic whole-program proof-coverage check. Compiler, hardware, composition and trusted-base assumptions remain. AWS's alternate SHA3 integration, Rust API, hybrid composition and this application are not thereby proved. Power/EM, speculative/frequency and fault attacks are outside that assessment. Current upstream assessment is evidence about components, not certification of the exact vendored binary or a blanket independent audit.

The selected build is non-FIPS. Enabling an optional FIPS feature would not establish a validated deployment. This suite provides an ML-KEM-768/X25519 confidentiality direction with classical Ed25519 authentication. Static recipient keys provide neither forward secrecy against their later compromise nor post-compromise recovery. Source read entitlement, complete keyholder accounting, authenticated catalog roots and exact accepted transition handling remain protocol obligations independent of provider choice.
