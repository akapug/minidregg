# Mini extensible persistent objects: resolved specifications and safe change

2026-10-02. **READ** denotes inspected source/text; **DERIVED** denotes consequences; **PROPOSED** is a construction contract, not existing behavior. Source baseline is immutable `b57acedaaae02edf2b2cfd8e33675b3cbf40daa8`, read with remote `git show` from persvati. No implementation, build, test, service action, or deployment qualification occurred. I read Mini AGENTS/HANDOFF, the October 1 architecture study, earlier `fareoo-audit.md`, and selected original Faré texts. The audit's historical observations are hypotheses to recheck, not HEAD facts.

## 1. What already extends, and what does not

**READ:** Mini already has application-defined persistent data, immutable versioned program records, loaded policy source, and source-owned checked computation. `Compiler/CanonicalCellRegistry.lean` maps `declaredObject` to `EffectDeclaration.effectLayout` and `DeclaredEffectCell.materializer` (`layout`, `materializer`, `DeclaredCellLaw`). A new application prototype on this substrate is different from introducing a new kernel role/codec; the latter still changes the closed `Kind` interpreter. `Kernel/ResourceBirthPolicyController.lean:59–73,134–148` checks a complete birth descriptor against factory, kind encoding, funding, initial policies and grants. Its descriptor is not evidence of general open-recursive OO, nor is the factory template a fixed arbitrary application layout.

**READ:** `Compiler/NockProgramCodec.lean:137–161` defines evaluator-generic `Abi` with sample slots, output slots, libraries, fuel, door and context mode; `Program` contains evaluator, jam, ABI and evaluator params. `programId` hashes the entire canonical program record (349), including ABI and evaluator identity. Libraries are exact program digests, not mutable package names. `ResourceTransaction.checkClaim:683–697` loads the program and listed libraries from the directory, resolves an enabled compiled-in evaluator, checks evaluator agreement, and re-executes against kernel-built samples. These are meaningful extension points: friends can supply code to an existing interpreter without redefining admission.

**READ:** current compute remains a field-write ABI. `OutputSlot:119–124` identifies target ordinal, field and encoding. `ResourceTransaction.targetWrites:616–621` returns `none` for stream append, and `commandWrites:633`/`checkClaim:695` require all writes to have that representation. The ordinary transaction supports append (`Payload.append`, `computeTarget:412–421`), but a checked run cannot simply include one. Compute's merge therefore does not establish checked message emission. Door state/event persistence is likewise not arbitrary transport effects. Authority delegation/revocation is another distinct effect: `DeclaredResourceController.rawLeg` uses `authorityReadPatch` (54–59), not an authority-writing patch.

**READ:** `prepareTarget:493–511` computes and validates each post-state, checks final post law, and loads source selected by current authority policy identity/revision. `PreparedInvocation:709+` combines one directory, current authority, clock, targets, marker and run check. `Compiler/PolicySourceCell.record_immutable` makes source cells ROM; `Kernel/CanonicalPolicyRegistry.SelectionPayload` binds current registry address, exact canonical source, authenticated membership and compiled record. `Theory/PolicyInstall` carries version/predecessor; `Pred/Core` has first-order predicates, not `self`/`super` policy references. Revision succession is not specification composition.

**DERIVED:** callable, durable, replaceable behaviors are already feasible. Intralinguistic ordered extension of somebody else's partial method specification is not demonstrated by these mechanisms. There is also no checked migration contract established by this reading. Neither statement implies the platform needs a universal plugin framework.

## 2. Three choices, with one preferred hypothesis

**A — restrictive inherited laws. PROPOSED:** resolve named versioned parent policies plus typed projections and evaluate conjunction. This is useful for an immutable minimum safety envelope. For a fixed resolved closure and projection, acceptance implies each parent accepts. It cannot express general around methods, open recursion, or overriding a parent's returned value. Boolean acceptance does not need C3; diagnostics and provenance still need canonical order. Live parents require guards, cycle checks and compatible projections. An append-only containment tree does not prove its live policy dependencies immutable.

**B — ordered open method extension. PROPOSED:** fragments consume complete `self` and previous `super`; an explicitly ordered chain produces the closed method. Faré's [2024 Essence of OO](https://fare.tunes.org/files/cs/poof/eoomi2024.pdf), §§3.1,3.3.5,4.1–4.3, is a better answer than a new versioning paper to what “extension” means: open recursion supports modular references, incremental composition operates on existing definitions, and order matters. His [2021 model](https://fare.tunes.org/files/cs/poof.pdf), §§1.1–1.3, supplies the small functional algebra. Mini can evaluate a closed result through its existing program mechanism, but the compiler/linker must bind composition order and dependencies. The outer authority/effect validator remains authoritative even if methods override one another. Costs include termination/fuel, unresolved-method checks, conflict/diamond rules and composition provenance. Multiple inheritance is optional; manually ordered mixins are already meaningful OO.

**C — immutable versioned program/descriptor composition. PROPOSED, preferred first experiment:** put a small application specification in declared data: exact layout/interface version, method-to-program mapping, ordered fragment/library references, default law and approved migrations. Compile/link its partial methods to an immutable existing `Program`; store a digest binding the ordered source closure to that result. Existing instances pin layout; a separately authorized head selects successors. Keep law revision/current grants distinct from code version. This makes B usable without first installing arbitrary native modules or generalizing every kernel role. Start with one board method, one interface and one migration; add dynamic interpreter roles only when this substrate proves insufficient.

**DERIVED:** A and C compose well: restrictive envelope outside extensible computation. A is not Faré OO by itself. C must actually retain partial fragments and late-bound composition to claim B; publishing unrelated replacement programs alone is versioned object-based computation.

## 3. Concrete invocation snapshot contract

**PROPOSED:** resolve once at the admission cut. Bind stable command/program identity and the necessary authorization footprint to signed intent; bind receiver-resolved current roots through settlement guards and admitted receipt evidence. Do not sign the whole authority root: `ResourceTransaction.Command:64–78` explicitly avoids that coupling. The combined record must identify:

1. Domain and admission semantics identity; request origin/id, signer, nonce/nullifier, target identities, version/pre-root and height validity window.
2. Instance descriptor/layout and interface/projection digest; method selector; exact closed program id, evaluator id, ABI, params/fuel; ordered fragment and library dependency closure with canonical edge/order encoding. Reject missing references, cycles, unsupported evaluator and inconsistent binding.
3. Exact current authority cell root, grant lineage/generation, applicable law ids/revisions/source digests, and clock root. Mutable descriptor heads and policy selection references belong in the read footprint; immutable content records belong in the available authenticated closure.
4. Exact sample inputs and all semantic reads, post-state/effects, emission envelopes and disclosed view. Read/write/authority footprint includes dependencies beyond the object's own fields.

Resolve/head selection must be deterministic, bounded, and read-guarded. If a signed operation selects a closure no longer permitted under current rules, refuse/reprepare; never quietly relink its same signature against another method. Old code identity can remain pinned while current law denies execution. This preserves Mini's current-authority principle and allows deliberate lockout. Historical replay needs the admitted closure and interpreter identity, not a fresh lookup of “latest.”

### Emitting under today's ABI

**PROPOSED compatibility experiment:** a checked program writes a bounded canonical message-intent noun into a declared object field, together with durable sequence/status. A receiving adapter reads the exact admitted intent and source receipt, constructs a separately authorized append, and records intent consumption. This is a new application outbox intent, **not** existing `FnOriginOutbox`: the latter is an origin-record/carrier custody mechanism, whose reuse needs a separate binding analysis.

The essential proof is `adapterAccepted => appendEnvelope = decode(programProducedIntent)` for the exact originating admission, destination, payload digest, authority ceiling and id. Checking merely that an arbitrary intent cell exists permits substitution. Consumption/receipt must bind source id and prevent duplicate semantic effects despite retries. Adapter authority permits delivery of that intent; it does not entitle the adapter to choose another recipient or invoke any method. Two admissions mean a committed intent can be undeliverable after revocation; expose pending/refused status, rather than claiming atomic remote effect.

For atomic local update-plus-emission, redesigning the ABI is viable: extend evaluator-decoded output to typed effects, then compare the entire canonical effect list with the signed command and validate each target/current authority. This changes output decoding, codec identity, exact-match/run theorems and laws; it is a deliberate kernel change. Keep actual network send outside admission and bind custody to admitted emission. An authority-write effect requires its own semantics, not a generic field-write disguise.

## 4. Migrating an in-flight message without amplified authority

**PROPOSED:** message `m` carries original signed bytes/id, source admission receipt, old descriptor/method/closure and semantic operation—not just field positions. Migration `U: v1→v2` is an authorized immutable artifact relating old/new states and requests. It records source/destination versions, target-id map, old/new interface projections, result/effect relation and permitted drops. New envelope retains old signature as evidence; an authorized migration admission signs/records `m2 = U.request(m)` and lineage. It must not pretend the old signature authenticates changed bytes.

The central obligation is semantic simulation: for related states and an eligible original request, executing its translation yields related states/effects; translated permitted effects are contained in the old operation's authority meaning, intersected with **current** authority. Use operation/observation relations, not numeric field-subset tests. Retained grant identity/revocation status, audience, target bounds, budget and nonce lineage are checked again. If translation needs extra authority, stop pending and require an explicit new authorization. No fallback owner bypass. Preserve causal predecessors and message id; one migrated message and its original share a consumption lineage, preventing both versions taking effect. Preserve/re-encrypt payload only under explicitly authorized destination audience; migration permission is not decrypt/read permission.

**Minimal trace:** v1 field 3 means public title. Bea signs `set(field3,"hello")` under title-only authority. Before arrival, Ari installs v2 where field 3 means room membership and title is field 7. A byte-preserving “compatible” update now grants membership; same numeric scope did not attenuate semantic power. A typed migration maps `setTitle` to field 7, keeps Bea's origin/id, and rechecks current title-write grant. If Bea was revoked between send and receive, it refuses. A permissive adapter with its own membership-management grant must not rescue it. This distinguishes replacement-by-head, schema conversion, and authority-preserving migration.

A second discriminator for A/B: parent method returns `x+1`; child around-method doubles `super(x)`. Reversing order yields `2x+1` versus `2x+2`. Conjoining two acceptance predicates cannot represent this distinction. For inherited security laws, adding a room clause that reads private field 9 must not silently give an inherited evaluator access to field 9.

## 5. What recent research adds, and what remains unproved

**READ:** [Cambria](https://www.inkandswitch.com/cambria/) (2020 essay; [2021 paper](https://doi.org/10.1145/3447865.3457963)), inspected schema/versioning, lens operators and limitations, transforms documents, edits and schemas across explicit versions. It supports decentralized customization better than a single universal head. **DERIVED:** structural edit conversion is useful for `U.request`; it does not establish authorization simulation, ciphertext access or causal/duplicate safety.

**READ:** Edwards et al., [Schema Evolution in Interactive Programming Systems](https://arxiv.org/pdf/2412.06269), published October 15, 2024 (journal 2025), §§1–3, identifies schema/code/data and local/non-local dimensions and supplies challenge problems; it expressly does not solve the full range. **DERIVED:** use its dimensions to test descriptor changes together with code and pending events, not to justify a migration theorem.

**READ:** Wyns et al., [Dynamic Software Updates using CRDTs](https://arxiv.org/html/2606.10920v1), June 9, 2026 v1, §§3.1–3.3,4.2,6: replicates versioned code, uses teardown/init, translates older messages and buffers newer ones. Model excludes Byzantine faults; invariant preservation is developer responsibility. Same-version distinct code can fail convergence; §6 acknowledges this. **DERIVED:** borrow explicit message version/carry lineage, not max-version-wins authority or unconditional eventual delivery. Semver is a publication convention ([2.0.0 spec](https://semver.org/spec/v2.0.0.html), §§1–11), not proof that two methods/effects are compatible.

**READ:** [Kitsune](https://mhicks.me/papers/kitsune.pdf), OOPSLA 2012, §§2.2–2.3,5, makes update points/control and state transfer explicit; it does not prove Mini's distributed authority claims. Faré's [2024 persistence model](https://github.com/mighty-gerbils/gerbil-persist/blob/master/persist.md), Schema Upgrade and cross-domain atomicity sections, already explains why ongoing activity must survive and why cross-domain cuts cost coordination. These older answers fit Mini's admission boundary better than VM migration throughput papers discovered in the recent search.

**PROPOSED adversary/failure model:** malicious submitter or adapter substitutes closures/effects, operator equivocates about heads, revocation races delivery, replicas retain older versions, crashes/retries duplicate messages, missing source prevents replay, migration leaks private projections. Existing clear executor remains trusted for confidentiality. Unproved obligations: complete authenticated closure/read footprint, compilation binding, simulation including effects/observations, conservation/exclusive identity mapping, no authority resurrection, durable deduplication across migration and receipt lineage. Source checks here establish fit only. The decisive experiment is the title/membership trace plus crash after intent commit, revocation before delivery, and exact replay across descriptor migration.
