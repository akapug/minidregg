# Checked result recovery and faithful typed evolution

Read-only current isolated source review, October 2. No edits/builds. Event41 receipt replay deliberately exports only transaction/result digest. Actual output is retained in signed execution.run.outputJam and theorem retained_result_is_checked_output connects it to the evaluator verdict. This is good custody, but not yet a complete recoverable-result native contract.

## Result recovery decision

Implement **explicit checked result custody with current gated historical export**, then permit addressed reply intents over the same custody/release contract. Transaction ID remains a selector, never read authority. Do not add raw result bytes to receipt replay.

A checked program output may contain arbitrary data, not only effects visible on its destination. It can derive from multiple target preimages, supplied arguments, dependent program inputs and private values. Observing today's destination cannot authorize that entire historical output. Neither can an originator's original invoke grant. Current NativeObservationController derives exact joint observation targets and ResourceObservationAdmission runs current observation grants/read laws on one loaded snapshot; reuse that mechanism rather than inventing an unrestricted history read.

The straightforward complete contract adds a source-owned **result custody resource/policy selection** to the supported method descriptor and event41 binding. Its policy governs exactly the complete retained checked result as an intentional declassification. Result creation must be authorized by the existing execution method's output/reply contract; arbitrary caller selection of a permissive custody resource must refuse. Whole-result access is explicit; field-scoped grants cannot silently export an unrestricted outputJam. Initially require unrestricted observation scope on this custody resource or implement a canonical typed projection.

Fresh result export authenticates a signed native recovery intent binding identity, retained event index/result digest, custody resource, requester, current challenge world root/clock and requested projection. Verify event41 against its authenticated historical prefix; derive exact retained output; load CURRENT custody resource, capability lineage and law; evaluate observation with the exact historical result context/digest, not only a current unrelated cell. Return payload only after admission. Mask preauthentication history/selector failures as undisclosed using the existing observation convention. Challenge expiry/root change gives normal retry; querying does not execute the method.

Do not assume existing ResourceObservationAdmission authorizes arbitrary context bytes: its current law must explicitly recognize the result-recovery purpose and bound result digest/bytes. The first implementation can persist the complete result as typed custody content at event41, atomically with execution/dedup, then reuse ordinary at-height content observation under its current policy. This costs an extra result-sized custody record but offers the cleanest native implementation and bounded projections. If referencing event41 output without another copy, add a specifically named result-view projection whose source proof binds that reference; price the extra proof/API work honestly.

A method lacking an explicit result declassification contract may still execute and return only a receipt. A conservative optional fallback must authorize every complete historical result dependency (target scopes, argument provenance and historical access rules). Current target-list analysis alone does not establish that closure for arbitrary program outputs, so do not claim this fallback exists.

## Checked reply intents versus gated export

| Contract | Benefit | Cost/obligation |
|---|---|---|
| Current gated historical custody export | Lost ACK recoverable directly; current revoke/read laws apply | Signed challenge/read API and result custody/projection; user needs surviving current read authority |
| Checked addressed reply intent committed with event41 | Autonomous sender receives result through durable messaging and delivery retry | Explicit recipient/reply authority ceiling; checked payload/result binding; another outbox/release/consumption lifecycle, correlation and possible reply-loop budgets |

Reply intents should be actual checked evaluator effects or a descriptor-declared exact result projection generated by the source-owned receiver; never an adapter-authored arbitrary payload. They bind original consumed input identity, result digest, selected bytes and reply destination. Exact previously authorized release may finish after revoke; fresh release must pass current authority. Inlining a reply after durable ACK without an outbox creates a crash gap. Gated export remains necessary for recovery when reply delivery or recipient availability fails.

## Typed behavior evolution decision

For the minimum faithful integration, **publish an immutable typed descriptor v2 and method program derived from a declared parent extension, then install its new head through existing authorized policy install**. Keep old descriptor/program cells. ObjectSpecificationBinding.check already loads typed descriptors, checks current required descriptor equals signed meaning, verifies complete typed method contract and program ID. Therefore an unconsumed old request should refuse after head change; never rebind its method name to new code. A consumed old request returns its original digest and authorized retained payload without rerunning under the new head.

Current Source.previous/compose is scalar static syntax extension. TypedDescriptor stores full methods but has no equivalent checked parent-extension composer or parent provenance relation. Add typed extension construction over the same supported bare-gate Nock fragment: decode inherited battery, close explicit previous syntax, rebuild computed-effect program preserving/explicitly changing typed ABI, validate TypedMethod.WellFormed, publish resulting immutable source. Bind parent descriptor/method and exact derivation in the authoring/install contract. This supports actual previous-behavior extension; it is not general open recursion or a behavioral-refinement theorem. Explicit effect contract changes still require ordinary authorization.

For this stage, same ABI/roles and supported parent extension are enough for useful versioned evolution. Demonstrate increment/append plus inherited behavior at new head, not mere replacement byte publication. Do not advertise pending-request translation: Kernel/ObjectMigration currently takes scalar Descriptor/Selection and requires same-profile original signature. Its authority relation is not native v2 typed migration dispatch. Typed translation is a separate larger path needing full slot/meaning attenuation, original/translated signatures, checked control leg guard composition, and one stable consumption lineage.

Native fixtures: execute old typed request, activate new descriptor, recover exact old checked result; replay duplicate with changed placement and new proposed output without second effect; refuse stale unconsumed old meaning; execute new meaning and exhibit inherited result; reject unchecked parent/ABI/role mutation; revoke result observation then deny fresh recovery while prior exact reply release remains recoverable. These complete actual result/evolution use rather than substituting compilation for it.

## Preferred completion after examining the existing reply composition

The root identified an existing route that improves the recommendation above: checked invocation event41 can emit a typed notification intent into an outbox atomically; event40 already recognizes event41 origins; notification event41 deposits it in the original sender mailbox; existing currently authorized mailbox observation recovers payload. **Prefer completing this route before adding a new result resource or privileged history surface.** It gives recoverability for the explicitly declared method reply. Arbitrary outputJam remains commitment-only and is not implicitly declassified.

The same capability can cover receiver, outbox and mailbox: TargetSet.explicit supports a finite target set (or an appropriate under-room scope). It must retain original principal holder, necessary mutation/append/observation verbs, field scope, budget, current lineage and each target's current law. Current consumption enforces exact ceiling ID on every target, so fixture delegation must deliberately include the outbox. Reply notification consumption still needs the notification's exact current ceiling for mailbox; incoming capability and emitted reply ceiling need not be the same identity, but each is source-owned and checked at its corresponding stage. Transport authority cannot substitute.

Missing binding/API obligations for this route:
- A canonical checked ReplyEnvelope must bind original consumed Identity/input digest, reply status, typed result payload and result schema/method meaning. MessageIntent has no reply-to field. Do not correlate by mutable placement or transaction ID alone.
- Program arguments currently equal immutable request payload. Put authenticated reply address/ceiling/correlation data into that payload, and require the immutable method contract to use/validate it. The worker must not invent recipient or payload after checking.
- `Receipt.resultDigest` hashes full outputJam, not notification payload. Provide an explicit checked reply payload digest/association rather than falsely comparing these hashes. Sender verifies reply origin's event41 consumption identity against envelope correlation.
- Native worker/CLI fixture must execute the whole route and recover mailbox content after sender loses both invoke ACK and reply ACK. Duplicate original invocation must return its consumed receipt without emitting another reply; duplicate notification deposits at most once; outbox scanning retries the original pending reply.
- Source current release laws/audience must authorize every intended holder. Current notification write admission skips origin invocation-ceilingCheck; later source release and destination consumption checks remain mandatory.

Retained mailbox policy and payload availability become the method-result recovery contract; full evaluator output recovery is intentionally a different contract. If mailbox observation rights are revoked, fresh reads refuse. Already authorized exact release retry remains distinct. Current receiving requires a fresh original-principal signature for execution, so autonomous offline delivery still needs explicit delegated signing/envelope evolution; the checked reply path does not resolve that independently.
