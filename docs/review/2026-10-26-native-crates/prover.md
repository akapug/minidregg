## EXECUTIVE SUMMARY

`prover` is an **unverified arithmetic library plus three Lean-emitted dispatch modules**. It has no network, file, socket or env-var surface in the library. Four manual binaries print benchmarks and cost models. It holds scalar BabyBear and a BabyBear sextic extension, a 64-bit and a 256-bit Fan–Paar binary tower, an additive NTT, MLE/fold kernels, raw cSHAKE256, a degree-1 and degree-3 sumcheck prover **and verifier**, a zkML matmul-contraction prover/verifier and a rank-1 gradient check. On top of that sits a generated `dispatch_native` seam for native works 9101/9102/9103, whose request/response codecs and pins Lean emits (`Compiler/NativeGlueGen.lean`).

Key findings:
1. **The crate cannot be built today.** Every cargo command in `prover/` fails with "current package believes it's in a workspace when it's not". The root `[workspace]` arrived on 2026-10-08 (`295cab11`), and since then no prover test, conformance vector or benchmark has run. `scripts/run-native-dispatch-benchmark.sh` and `run-sparse-equality-benchmark.sh` are broken. `scripts/check-prover-glue.sh` compares bytes only and still passes.
2. **It is an island.** No crate in the workspace, no script and no Lean `@[extern]`/process spawn invokes it. Lean's byte controllers compute the "native" replies themselves. Nothing in the host wire (`protocol/host-operations.json`, `Host/Json.lean`) names it. **A public demo needs zero lines of it.**
3. The untracked Uwueave pair is **red twice**. `uwueave_preo_projection_v2.rs [not in tree]` imports a module that `src/lib.rs` never declares. `Compiler/UwueavePreoProjectionV2.lean` imports `Uwueave`, which `lakefile.toml` does not require.
4. Rust **authors** several things: field constants (two-adic generator, Ext6 `W = 31`), the tower basis, the sumcheck wire format (Lagrange evals at {0..3}, while Lean uses coefficient form), and verifier verdicts (`verify_sumcheck`, `verify_cubic_sumcheck`, `verify_matmul`, `rank1_accepts`, …). Its own doc comments admit each one. All of it is latent: none of it is wired.
5. Heavy internal twinning: five MLE evaluators, three folds, two eq-tables, two Fan–Paar multipliers, two additive-NTT recursions and three overlapping generated dispatch catalogs.
6. A GF(2^256) multiply costs **13–38 µs**, per the committed dispatch logs for vector length 1.

## 3. Does it decide anything semantic?

For each item: whether it is wired, and the Lean counterpart.

1. **Verifier verdicts in Rust.** `verify_sumcheck` (`sumcheck.rs:235-257`), `verify_cubic_sumcheck` (`:507-537`), `verify_matmul` (`:691-711`), `rank1_accepts` (`rank1.rs:171`), `rank_k_accepts` (`:178`), `sgd_step_accepts` (`:193`). Each returns `bool` acceptance. Lean counterparts: `Selvage/SumcheckReduction.lean` `SumcheckAccepts`, `Assurance/AirSumcheckCubic.lean`, `Assurance/ZkmlMatmulSumcheck.lean`, `Selvage/Rank1GradientCheck.lean`. **Unwired** (tests and benches only). Taken literally, ATLAS §7 forbids these: "Authors nothing". The EvmStage0 decision record quoted at `Compiler/EvmStage0NativeDeployment.lean:4-8` says deleted authority islands "must not be reintroduced as handwritten parallel protocol profiles". Git shows the pattern: `0b9031ab` "remove handwritten LogUp protocol mirrors" and `345a0cae` "delete orphan sumcheck mirror" (2026-08-09), then `fa2df24f` "regrow the Selvage sumcheck engine" (2026-08-13). The mirror has regrown. It is vector-bound and labelled honestly, but it is a second verifier.
2. **Sumcheck wire format.** Degree-3 messages are `[h(0),h(1),h(2),h(3)]` with Lagrange interpolation (`sumcheck.rs:57-73,296,310-330`). The doc states Lean keeps coefficient form, and that the char-2 tower "cannot use these nodes at all… an open fork" (`:67-73`). Rust chose a transcript shape Lean did not. Lean counterpart: `roundPoly`, coefficient form. **Unwired.**
3. **Field and extension constants.** `TWO_ADIC_GENERATOR` (`babybear.rs:13`) and `EXT6_W = 31` (`field6.rs:13-14`, "The Rust-selected reduction relation"). The Lean Ext6 proof uses the same 31 (`Ext6Conformance.lean`), but no emitted constant binds the two. The two-adic generator has no Lean counterpart found by grep in the artifact. **Wired** only inside `mle_kernels` Ext6 folds, which are themselves unwired.
4. **Tower basis and representation.** `binary_tower.rs:3-24` and `binary_tower_256.rs:3-23`. Lean counterpart: `Theory.BinaryTowerCodec`, `BinaryTower256Profile`. Same stated layout, no executable cross-check beyond GF(4)/GF(16) tables and generator relations. **Wired** through work 9101, where Lean's checker re-judges the bytes.
5. **MLE conventions** (LSB-first indexing, reversed-LCH bit order, multiplicative pairing): `mle_kernels.rs:3-9`. **Unwired.**
6. **Soundness-relevant parameter in a binary:** `LOG_BLOWUP = 2`, "the deployed blowup" (`low_rank_commit_cost.rs:49-51`), plus Poseidon2 rate 8. These are cost-model inputs, not protocol control, but they assert a deployment parameter that Lean does not emit. Lean counterpart: none found.
7. **Dispatch adapters: no semantic decision.** `native_dispatch.rs` makes only local error/success choices (length, canonicity, SSA discipline). Each reply is a candidate that Lean's `descriptorHoldsCheck` or Tower256 checker judges (`native_dispatch.rs:1-8,159-168`). The generated `from_ids` pin checks are Lean-emitted. **This is the sanctioned pattern.** It holds for 9101 and 9103. 9102 is a degenerate echo.
8. **Retry, funding, identity, ordering, dedup, pricing, admission:** none. The crate has no I/O.

## 4. Flaws, each with a concrete failure scenario

1. **Unbuildable since 2026-10-08.** `cargo tree --offline` in `prover/` errors: "current package believes it's in a workspace when it's not… add `prover` to `workspace.members`… or add an empty `[workspace]` table". Scenario: a developer runs `scripts/run-native-dispatch-benchmark.sh:7`, or any `cargo test --manifest-path prover/Cargo.toml`, and gets a hard error. Consequence: the five Lean-bound conformance suites have not executed for 18 days. Lean has re-emitted glue in that time (`fdce94dc` was 2026-09-30, and the payload changes continue), so a Rust/Lean divergence would go unseen. `scripts/check-prover-glue.sh` re-elaborates the emitters and `cmp`s bytes, but never compiles the result. "Glue OK" therefore says nothing about whether the glue compiles against `native_dispatch.rs`.
2. **The untracked Uwueave pair is red on both sides.** (a) `uwueave_preo_projection_v2.rs [not in tree]:8` uses `minidregg_prover::uwueave_preo_projection_v2::…`, but `src/lib.rs` has no such module. (b) The generated file already wraps everything in `pub mod uwueave_preo_projection_v2 {}` (`:4`). A naive `#[path] pub mod uwueave_preo_projection_v2;` would double-nest it, and the test's paths would still fail; it needs `include!` at the root or a re-export. (c) The Lean emitter `import Uwueave.Preo.ProjectionV2` (`Compiler/UwueavePreoProjectionV2.lean:15`) has no `[[require]]` in `lakefile.toml`, so that module cannot elaborate. (d) It is not in `check-prover-glue.sh`'s module list. Scenario: once flaw 1 is fixed, `cargo test` still fails to compile this target, and `cargo test` aborts the whole run on a compile error.
3. **"Fail-closed" verifiers panic on malformed input.** `verify_matmul` calls `mle2_eval`, which `assert!`s `rows == 1 << x.len()` (`sumcheck.rs:651,654`). `verify_sumcheck` delegates to a caller oracle that typically asserts dimension (`mle_eval`, `:121-126`). A proof whose round count equals its challenge count but not `m` reaches the oracle and panics. `rank_k_accepts` `assert_eq!`s its lengths (`rank1.rs:179`). Scenario: if any of these were ever wired to a peer-supplied proof, a crafted shape aborts the process (DoS) instead of returning `false`. The doc's "Every check REJECTS on failure — fail-closed" (`sumcheck.rs:230-233`) overstates what the code does.
4. **The Tower256 multiply is far too slow for any real use.** The committed logs show 37,707 ns per one-element dot on hbox (`benchmarks/native_dispatch/2026-08-09-hbox.log`, first data row) and 13,450 ns on persvati. That is about 26K–74K GF(2^256) multiplies per second, because the recursion goes down to GF(2) bits (`binary_tower_256.rs:229-254`). Scenario: a 2^20-point additive NTT (about 10^7 muls) would take minutes. The 9101 work is a toy at this speed. Nobody is harmed today, because nothing calls it.
5. **Three overlapping dispatch catalogs.** `semantic_artifact_v1` serves {9101}, `semantic_artifact_arithmetic` serves {9101, 9102} and `evm_stage0_add_aux` serves {9101, 9102, 9103}. Each has its own `NativeWorkRequestDto`, `dispatch_native` and canonical-artifact JSON, with different clause sets. Scenario: an integrator wires `semantic_artifact_v1::dispatch_native` (the module `native_dispatch_bench` uses, `src/bin/native_dispatch_bench.rs:15-20`) and every 9103 request returns `UnsupportedWork`. Or the integrator authenticates replies against the wrong artifact payload. Which artifact is current is decided by which module you import, not by Lean.
6. **Generated code lives in `src/`.** `src/semantic_artifact_arithmetic.rs` is `@generated` but sits beside hand-written code. A reviewer or tool that treats `src/` as hand-authored misreads it. A `generated/`-scoped lint would miss it.
7. **Provenance points at the wrong lock.** `scripts/local-check.sh:410-411` records `prover/Cargo.lock` as *the* `cargo_lock_sha`. Since 2026-10-08 the root `Cargo.lock` governs every deployed native crate. Scenario: a candidate snapshot's provenance attests a lock file that builds nothing deployed, while the real lock goes unrecorded.
8. **The cross-language vectors for Tower256 and Ext6 are weak.** As noted in §2, the only Lean-originated Tower256 vector is `1·1 = 1`. Ext6 "Lean vectors" are numerals in the test source (`prover/tests/field6_sumcheck_runtime.rs:55-75`), not a Lean-written file. A Rust multiply bug in the high limbs would pass the sentinel. Lean's 9101 checker would catch it at check time, but only once 9101 is actually dispatched (it is not).
9. **Lean elaboration writes the Rust tree.** Each `lake build` of `Compiler.*` rewrites `prover/testdata/*.json` and `prover/generated/*.rs` relative to cwd (§2). Scenario: building from a different cwd writes stray `prover/` trees elsewhere. `check-prover-glue.sh` exists precisely because concurrent sessions saw this as "drift" (`scripts/check-prover-glue.sh:9-13`).
10. **`baby_bear_add1_zero_witness_bytes` is a constant echo** (`native_dispatch.rs:144-152`). The "native work" returns bytes Lean already holds. It exercises the seam, but anyone reading the catalog would take it for a kernel.

Deleting it from the *repository* is a different question. ## 7. Deployability on a small public Linux VM

- **Build:** impossible as committed (§4.1). Once fixed, it needs a stable Rust ≥ 1.73 (`u64::div_ceil` in `low_rank_commit_cost.rs:61`, let-else). The benchmark logs show nightly 1.98/1.99. There is no `rust-toolchain.toml` (`local-check.sh:409` treats it as optional).
- **System deps:** none. Pure Rust, no C, no `build.rs`.
- **Ports, privileges, persistent state, secrets:** none. It is a library plus stdout-only binaries.
- **systemd:** not applicable. There is no daemon.
- **Fresh Debian:** it would fail at the workspace error before anything else. After that, the only thing needed is network access to crates.io for `sha3` (and serde for tests).
