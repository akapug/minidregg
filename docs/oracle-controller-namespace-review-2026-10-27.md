# Controller identity in the resident namespace

The provisioning operator is trusted with controller custody. It creates the controller, tool, dispatch and provider role keys, keeps their source copies under its workroom, supplies the controller binary and configuration, and invokes the existing trusted root installer. A controller ID chosen from that operator's delegated sub-ID range is therefore not a secret from that operator: the delegation also permits the operator to map that identity in another user namespace. This design does not claim to protect controller keys from their provisioning operator.

The separation protects Store and operator resources from controller and application execution, and keeps an application from impersonating the controller. The resident must see the controller's real numeric identity for peer credentials and filesystem access checks; an unmapped overflow identity is not an acceptable substitute. The intended mapping is exactly the root-registered operator, the world's selected app, and the root-registered controller, or just operator and app when no controller is installed. A controller-provided packet or resident JSON must not choose a mapping.

The existing resident bootstrap checks the root-owned world registry and broker-selected app identity before parsing resident JSON. It creates a user namespace, verifies the exact maps, forks the launch worker, and drops the parser to the operator and the worker to the app. The identity drop empties supplementary groups and capability sets, drops bounding capabilities, sets no-new-privileges and verifies the resulting identity. The parser also blocks creation and joining of new namespaces. These are source observations, not evidence that the proposed third-ID mapping or deployed receiving path has passed its tests.

The repair must reserve controller UID and GID in the operator's delegated intersection while refusing registered app ranges, other controller reservations, and conflicting existing accounts/groups. Later world allocations must refuse those reservations. Malformed or unsafe root records must fail closed. The eventual Linux checks should exercise the real maps and confirm the controller cannot claim the operator ID or retain bootstrap capabilities, the app cannot claim the controller ID, a substituted or absent required receipt cannot select an ID, and ordinary worlds still receive only the original two mappings.

A namespace keeps its mappings for its lifetime. Removing a controller account or receipt does not remove its ID from an already-running resident. A removed controller's IDs therefore must not be silently reused by a future world or controller while any old namespace can remain; retained removal receipts must be enforced as reservations, or removal must establish and serialize complete resident shutdown before reuse. A root administrator can still explicitly change host identities and is within the host trust boundary.
