# Installing the app market on the demo box

What the infra lane applies (dregg-infra `demo-vm`, `edge/demo/`) and what the candidate ships, for
`docs/APP-MARKET-2026-10-27.md`. Every path below is on `dregg-demo`; nothing here holds a secret.

## 0. Genesis: what the world must carry to host grains at all

A Mini world hosts SPK grains only if its pinned config carries the grain platform's operator policy
(the Host config fields `lifecycleManagement`, `completionCustodianKey`, `grainBirthTariff`; the workroom
fixtures pin them through `WORKROOM_OPERATOR_POLICY`, `same-store-profile.py` and
`composed-inputs.sh` refuse `operatorPolicyRequired` without them). Rehearsal #3 is a re-genesis that
carries them (ruling 2026-10-27). The operator sets, in `genesis-params.json`:

```json
"grainPlatform": {
  "lifecycleManagement": {"managementSubject": 7, "managementKeyId": 7007},
  "grainBirthTariff": {"base": 2, "perBirth": 1},
  "completionCustodianKey": null
}
```

| field | what it is | who holds the key |
|---|---|---|
| `lifecycleManagement.managementSubject`, `managementKeyId` | the subject whose key authors every grain's lifecycle (INSTALL BEGIN/CLAIM/COMPLETION, routes, the worker's share issues). A **Host setting**, not a genesis parameter: `run.sh platform --state DIR --management-subject S --management-key K` rewrites it in the pinned config and restarts a Store `run.sh start` launched (a unit-managed Store: stop the unit, run `platform`, start the unit) (applications already born keep the manager their own laws bound at birth; new births take the new one). The sponsor (7/7007 in the demo params) is the natural first value because `run.sh init` generates its key | `mini-core`: the named subject's key under `store/node/keys/` (0700 directory, 0600 files), generated by `run.sh init` as `mini-core` for the sponsor; no root-held copy, no copy off the box |
| `grainBirthTariff.base`, `perBirth` | the metered cost of one grain-family birth, in the metered task's units: `base` + `perBirth` per resource; an application birth (three resources) costs `2 + 3 × 1 = 5` units with the defaults, which is why the install reserves 5 on the tool task (`MINI_REENROLL_APPS_MAX` 50000 bounds one operation, §4) | the Host pins it; L1b's tariff ruling may raise it |
| `completionCustodianKey` | the public key (32 bytes, lowercase hex) of the completion custodian: the key that signs each lifecycle step's physical report (`spk-host grain`'s `completionCustodianSeed`); `null` in the operator's file | `mini-core`, `store/node/keys/completion.seed` + `.pub`: `run.sh init` generates the pair when the field is `null` and fills the hex before the genesis template runs (`mini keygen --no-prerotation`); never copied anywhere, never held by root |

Checks: `params.sh require-platform genesis-params.json` before `run.sh init` (refuses by name a
missing block or field); after init, `jq '{lifecycleManagement, grainBirthTariff, completionCustodianKey}'
store/node/deployment/pinned-config.json` shows the three pinned values, and `keys/completion.seed` is
`mini-core` 0600. `mini apps bootstrap` (§4 step 0) then births the metered tasks on that world.

## 1. Accounts and groups (install-demo.sh, split tenancy)

| account / group | why |
|---|---|
| user `mini-market` (nologin, primary group `mini-apps`) | the fetcher; the one uid with egress to the app index |
| user `mini-apps-edge` (nologin, primary group `mini-edge`) | the grain front; connects to route sockets, nothing else |
| group `mini-apps` | readers of the quarantine: `mini-market` writes it, `mini-core` (the worker) reads it |
| group `mini-edge` | the edge: `mini-apps-edge` is a member; the worker's unit carries `SupplementaryGroups=mini-edge` (membership inside that process only, never the account), so the worker can create `edge.sock` with that group |
| `mini-core` | unchanged, plus membership of group `mini-apps` (below); the worker runs as a SYSTEM unit with `User=mini-core` and drives `mini-spk-broker@` in mini-core's user manager through `/run/user/UID` |

`mini-core` must be in `mini-apps` to read the quarantine (0750/0640, group `mini-apps`); add it where the accounts are made:

```
usermod -aG mini-apps mini-core     # new processes only: restart the worker after this
```

```
/var/lib/mini-apps                   mini-core:mini-core 0711   (NOT under /var/lib/mini: the front must traverse it; mini-core-owned because the worker, running as mini-core, binds edge.sock here and creates origins/ verdicts/ requests/ grains/ work/ exports/ itself)
  origins/                           mini-core 0755             a<app>.json 0644, read by the front
  edge.sock                          mini-core:mini-edge 0660   the edge connector: the front asks `connect {grain, route}` and receives the custodian socket (SCM_RIGHTS); created by the worker
  verdicts/                          mini-core 0755             ID.json 0644, the ingest's verdict the catalogue shows
  requests/ grains/ work/ exports/   mini-core 0700             the worker's private state
/run/mini-apps                       mini-core:mini-sessions 0750  worker.sock 0660 mini-core:mini-sessions (members connect; SO_PEERCRED names them); tmpfiles.d: `d /run/mini-apps 0750 mini-core mini-sessions -`

```

Route sockets stay where `spk-host grain route` puts them, under the operator's 0700 state root;
no `routes/` directory under `/var/lib/mini-apps` is needed: the front reaches a grain through the
worker's edge connector (design doc §4), which adds no authority.

Add to `edge/demo/host/nftables.conf` and `demo-egress-resolve`, in the shape of the existing rows:

|---|---|---|---|
| `mini-market.service` (`cg_market`) | `mini-market` | hosts of `/etc/mini/market.json .index` and `.packages` (`app-index.sandstorm.io`) | 443 (+53 to the resolvers) |

The service drop-in `60-demo-confine.conf` adds `NFTSet=cgroup:inet:filter:cg_market`. Every other

## 4. Units (ship with the candidate; this directory)

```
install -m 0755 deploy/market/mini-market-fetch /usr/local/lib/mini/market/mini-market-fetch
install -m 0644 deploy/market/mini-market.{service,timer,path} deploy/market/mini-apps-front.service /etc/systemd/system/
install -m 0644 deploy/market/mini-apps-worker@.service /etc/systemd/system/     # a SYSTEM unit (User=mini-core): a user manager cannot setgroups for SupplementaryGroups (216/GROUP)
echo 'd /run/mini-apps 0750 mini-core mini-sessions -' >/etc/tmpfiles.d/mini-apps.conf && systemd-tmpfiles --create
install -d -m 0711 -o mini-core -g mini-core /var/lib/mini-apps
systemctl enable --now mini-market.timer mini-market.path mini-apps-front.service
systemctl start mini-market.service          # the first index refresh, so the catalogue is there before a member asks
# the uid is the box's: a system unit cannot learn it (%U is 0 there), so a drop-in carries it
uid=$(id -u mini-core)
install -d /etc/systemd/system/mini-apps-worker@.service.d
cat >/etc/systemd/system/mini-apps-worker@.service.d/10-mini-core-uid.conf <<DROPIN
[Unit]
Requires=user@$uid.service
After=user@$uid.service
[Service]
Environment=XDG_RUNTIME_DIR=/run/user/$uid
Environment=DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/$uid/bus
DROPIN
systemctl daemon-reload
systemctl enable --now mini-apps-worker@STORE.service
```

What the worker needs from mini-core's user manager, exactly: `spk-host grain start|stop|status` run
`systemctl --user` (`os::systemctl`, `hostd.rs`), which finds the manager through `XDG_RUNTIME_DIR`
(`/run/user/UID/systemd/private`; the bus address is the fallback), and the broker's runtime units
live under `/run/user/UID/systemd/user` (`os::runtime_units`, by effective uid, which `User=mini-core`
makes right). `mini-spk-broker@` is a user unit, so a system unit cannot order against it: the drop-in
orders after `user@UID.service` (the manager exists; `loginctl enable-linger mini-core` keeps it up).
The worker does not wait for the broker: a grain operation that finds it down answers `undecided`
with a retry command (`mini apps status --grain …`) and the member retries.

**Step 0, once per world, by the operator (ruling 2026-10-27): the metered tasks.** The demo's
genesis has no metered parent/tool tasks (7901/7902 are the workroom fixture's), so the apps world
births its own, as the operator (`mini-core`), from the operator's sponsor workspace, idempotently:

```
sudo -u mini-core /var/lib/mini/candidate/current/bin/mini apps bootstrap --dir /var/lib/mini/store/node/sponsor --budget 1000000
```

It births two `grain` resources under the operator's own capabilities (ids from the operator's
namespace; budget an explicit allocation), registers them as the sponsor's references `tool` and
`parent`, and prints `toolTask`, `parentTask`, the two sponsor import lines (already satisfied for
the sponsor workspace it ran in) and the exact `appsConfig` object to write to `/etc/mini/apps.json`.
A second run finds the references and prints the same report; a changed budget or names refuse by
name (one bootstrap per world). The sponsor's `delegate` in `apps_member_grants` then works against
those references.

`/etc/mini/apps.json` (root 0644, world-readable; `mini-apps-config-v1`) tells members what the
world is: `{"protocol":"mini-apps-config-v1","managementSubject":"8","toolRef":"tool","parentRef":"parent","tariff":{"base":"2","perBirth":"1"}}`.
A member's `apps install` births the application as their own op 30, whose admitted shape names the
world's metered parent (7901) and tool (7902) tasks. The frame grants them at enrolment
(dregg-infra `mini-reenroll`, `lib.sh apps_member_grants`, 400c94c); the three choices, confirmed:

1. **The grant bound** (`delegate ID REF SUBJECT observe,mutate MAX`): `MINI_REENROLL_APPS_MAX`
   **50000**. `MAX` bounds what one operation may charge under the delegated tool/parent
   capability, and the metered application birth charges it more than 1000: measured on dregg-build
   w3, the member's birth is refused `no-grant` at 1000 and passes the grant checks at 50000, the
   figure the workroom's own parent grant carries. The member's own account still bounds the total.

   **Bootstrap budget**: `mini apps bootstrap --budget 1000000` on the demo. The shared tool task's
   budget is consumed by every application birth (on w3 its `remaining` was down to 13 after
   about a dozen births); a million keeps the market open for the demo's lifetime. The sponsor's genesis balance
   must cover it (infra raises it).

   **What one install costs the member** (the door funds 10000): an ordinary birth (the request
   cell under `law.apps`) is **173**, measured on w3 (10000 -> 9827). The whole install (the
   three-resource application birth, the request cell, the six delegation proposals) is
   **about 1,500, an estimate** until the first member install lands and its measured debit
   replaces this line. The 5-unit reservation comes from the world's tool task, not the member, and
   is released by `settle 0` if the birth is refused. The receipt's `budget` line states the
   amount the install actually reserved.
2. **The sponsor's references** are named exactly as `apps.json`'s `toolRef` and `parentRef`
   (default `tool`, `parent`). `mini apps bootstrap` (step 0) registers them in the workspace it runs
   in; a sponsor workspace other than that one imports them with the two lines the bootstrap
   prints (`import tool object <toolTask> <cap> <cap>`, `import parent object <parentTask> <cap> <cap>`).
3. **Delivery to the member**: the frame copies each grant's `recipient-reference.json` to the
   member's `HOME/inbox/<toolRef>.json` and `HOME/inbox/<parentRef>.json` (member-owned; the
   shell's `inbox` lists that directory). `mini apps install` (with `--home`, which the shell passes)
   imports the two references from there by name before anything else, so a door member never runs
   an import by hand; only when neither the reference nor the inbox file exists does it refuse
   `meteredGrantRequired`, naming the file it looked for.

`mini-apps-worker@STORE.service` reads `/var/lib/mini-spk-worlds/STORE/apps-world.json` (the
operator writes it, 0600: `mini-apps-world-v1`, naming the grain-host profile, `mini`, the public
socket, the metered tool/parent tasks, the genesis, the quarantine, the market's `wanted/`, the
verdict directory, the domain and a nonce file). The worker creates `edge.sock` with group
`mini-edge` and `worker.sock` with group `mini-sessions` itself, under the unit's
`SupplementaryGroups`; a missing group is reported and refused, never silently 0600.

## 5. Caddy: the wildcard origin block

DNS: `*.demo.dregg.online` A/AAAA (live). TLS: the one `*.demo.dregg.online` certificate the infra
lane issues (Caddy built with the Gandi DNS module, DNS-01 off the box's own token policy as ember
ruled; hybrid key exchange first, classical fallback). **Routing rule: one entrance that dispatches by
`Host`.** Caddy proxies the whole wildcard to the front on `127.0.0.1:8799`; the front picks the
grain from `Host` and the participant route from the credential. Why not one upstream per grain: a
custodian socket is per participant, so a shared grain has several sockets and the choice is the
token's, which Caddy cannot look up (and token hashes do not belong in a Caddyfile that restarts per
share). Why not Caddy to the sockets: `/var/lib/mini` and the route files stay hidden from `caddy`.

```
# edge/demo/host/caddy/grain-origins.caddy — every market grain's origin, https://a<app>.@DOMAIN@.
# The explicit site blocks (@DOMAIN@, calc.@DOMAIN@, nano.@DOMAIN@) take precedence over the wildcard.
*.@DOMAIN@ {
	tls /etc/caddy/certs/wildcard.@DOMAIN@.crt /etc/caddy/certs/wildcard.@DOMAIN@.key {
		# Hybrid post-quantum key exchange first, then classical: browsers without ML-KEM still connect.
		curves x25519mlkem768 x25519 secp256r1
	}
	request_body {
		max_size 8MB
	}
	# The grain entrance (deploy/market/mini-apps-front.service). It needs the exact Host (the
	# custodian pins expectedHost) and no X-Forwarded-* rewriting of the request it forwards.
	reverse_proxy 127.0.0.1:8799 {
		header_up Host {host}
		header_up X-Real-IP {remote_host}
		transport http {
			dial_timeout 2s
			# A first GET through a fresh grain is a full Mini transaction (op36/37/34): minutes on a loaded Host.
			response_header_timeout 900s
		}
		# WebSockets: Caddy switches to a byte pump on 101; no idle deadline on upgraded streams.
	}
}
```

The box keeps its own Caddy-issued wildcard `tls` block (the Gandi DNS module the infra lane
built in) and takes only the proxy body above (`request_body`, `reverse_proxy 127.0.0.1:8799` with
its `header_up` and `transport` lines); the `tls` lines in the block are the file-based variant for
a box that installs the certificate as files. The 8 MiB body cap is the custodian's own bound (`http_entrance.rs`); the front
answers 413 above its 128-byte bootstrap-form bound.

## 5a. The publishing origin: `https://<grain>-www.demo.dregg.online`

Sandstorm apps publish a static site from the grain's `/var/www` (Hacker Slides' "Present" link,
blogs, wikis). The grain tells the app its publishing origin through `HackSessionContext.getPublicId`
(`native/spk-rpc`, `publishing_origin`): `publicId = <grain>-www`, `hostname = demo.dregg.online`,
`autoUrl = https://<grain>-www.demo.dregg.online`. One fixed publishing origin per grain, beside its
private origin, for the grain's lifetime.

**Caddy: no new route.** `<grain>-www.demo.dregg.online` is one label under `demo.dregg.online`, so
the wildcard site block of §5 already matches it, the wildcard certificate already covers it, and
it reaches the front at `127.0.0.1:8799` with `Host` intact. Nothing else changes on the box (no new
port, no new certificate name, no egress).

**The front's handling** (`mini apps-front`, by `Host`):

| request | answer |
|---|---|
| `GET`/`HEAD` `https://a<n>-www.…/<path>`, grain `a<n>` in the origin table | the file `<path>` under the grain's `/var/www` (`/`, a trailing `/` and a directory read `index.html`), anonymous: the front forwards only the method and the path, never a cookie or a credential; `Content-Type` by extension, `X-Content-Type-Options: nosniff`, `Cache-Control: no-cache`, `Referrer-Policy: no-referrer`; an SVG also carries `Content-Security-Policy: sandbox` (shown, never run). HTML runs as published: the `-www` origin is its own origin with no cookies, so a published deck's scripts reach nothing private |
| any other method | `405`, `Allow: GET, HEAD` |
| a path with `..`, `.`, a dotfile segment, NUL, a backslash, an encoded `/`, or a symlink anywhere on it | `404 no such published file` (each component opened with `O_NOFOLLOW` beneath the tree's descriptor) |
| a file above 64 MiB | `413` |
| an unknown grain, or a grain whose app has no `/var/www` | `404 no such published site` |
| the grain stopped (no resident listening) | `503 grain a<n> is stopped; its owner starts it with mini apps start --grain a<n>`, `Retry-After: 30` |
| more than 16 concurrent publishing connections on one grain | `503`, `Retry-After: 5` |

The files come from the grain's resident. The grain's `/var` is the app's 0700 mount and Sandstorm
publishes all of `/var/www` whatever its files' modes, so each file is opened by the app-identity
launch worker (`resident_privilege.rs`, tag 6: checked path components in, one read-only regular-file
descriptor out) and only read by the resident (`native/spk-host/src/www_publish.rs`); a connection
thread parses the request and the resident's loop, which owns the worker channel, answers it. The
resident binds `apps/<app>/www.sock` (0600, the operator's) beside the generations; the worker's edge
connector answers `{"verb":"www","grain":…}` with a connected stream, as it does `connect` for
`http.sock`, or refuses `grainStopped` /
`unknownGrain` by name. Publishing is the app's own act (it writes `/var/www`); the grain's private
origin and its cookies are never reachable from the `-www` origin (different host, `__Host-`
cookies are origin-bound).

**State**: built and tested (`spk-host` `www_publish` tests, `mini` `apps_front_serves_the_publishing_origin…`
and the connector's `www` verb); proven on a box by the `www` row of the lane's box run.

## 6. What a stranger sees

`https://a4501.demo.dregg.online/` without a credential: `403 private grain a4501; open it from your
Mini shell: mini apps open --grain a4501`. `GET /__mini/bootstrap`: the tokenless sign-in form;
POSTing the one-time bootstrap token `mini apps open` printed sets the `__Host-mini_spk_session`
cookie for that origin only. An unknown `a<n>`: `404 no such grain`. Nothing in these answers calls
Mini or writes a record.
